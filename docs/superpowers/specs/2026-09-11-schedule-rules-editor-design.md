# Расписания: редактор правилами вместо сетки по дням

Дата: 2026-09-11. Статус: направление утверждено пользователем в разговоре;
детали — в этом документе, на утверждение.

Развивает спецификацию `2026-09-04-structured-schedules-design.md`. Хранение,
серверная проверка и выгрузка из неё остаются; меняются редактор, канонический
текст и одно дополнение модели дня.

## Зачем

Первая версия редактора показывала семь раскрытых дней, у каждого — тринадцать
элементов (три кнопки состояния, копирование, две подписи, два поля времени,
«до конца дня», «×», метка, «+ интервал» и подсказка под ним). Семь дней × два
поля = больше ста элементов на одном шаге; всё сливалось. Пользователь: «ужасное
интерфейсное решение, всё сливается, куча кнопок».

Живые графики лаунжей, которые пользователь привёл как частые:

| № | Как говорят операторы |
|---|---|
| 1 | Пн–Пт 09:00–21:00; Сб–Вс 10:00–20:00 |
| 2 | Пн–Пт 02:00–01:00; Сб–Вс 05:00–01:00 (до часу ночи следующего дня) |
| 3 | Пн–Вс 07:00–22:00 |
| 4 | Пн–Вс 00:00–23:59 (круглосуточно) |
| 5 | Пн, Вт, Ср, Чт, Сб, Вс 09:00–21:00; пятница не работает |
| 6 | Пн–Вс «с первого вылета по последний вылет» (очень часто у небольших аэропортов) |

Плюс два требования: должна оставаться возможность задать в каждый день своё
время, и лаунж может работать всего пару дней в неделю.

Из таблицы видно главное: операторы думают **правилами** — «эти дни — такой
режим», а не семью отдельными днями. Пять из шести примеров — одно или два
правила. Два примера первая версия не выражала вовсе: переход через полночь
(№2) и «по расписанию рейсов» (№6).

## Решения пользователя

- Ввод — правилами: набор дней + режим. Семь разных дней — семь правил.
- Ночной график вводится как есть («02:00–01:00»), а **хранится разбитым по
  суткам**: «02:00–24:00» в этот день и «00:00–01:00» в следующий. Модель
  хранения не получает интервалов через полночь.
- «По расписанию рейсов» — отдельное состояние без времени.
- Дни, не попавшие ни в одно правило, — закрыты; это написано под правилами.

Уточнение, принятое при записи (пользователь сказал «грубо говоря 23:59»):
конец суток хранится как `24:00` — это уже законное значение `to` в модели,
оно не теряет минуту и сохраняет непрерывность «24:00 → 00:00», по которой
редактор узнаёт ночной график при чтении. В выгрузке дня печатается `24:00`.

## Что НЕ меняется

- Хранение: `WeekHours` — семь дней, у дня `allDay` / `none` / `windows`,
  интервалы в пределах суток, `to > from`, без пересечений. Значение в том же
  jsonb-столбце, миграции нет. Уже сохранённые структурные ответы остаются
  валидными и читаются новым редактором без конверсии.
- Серверные ворота (`validateField` → `weekHoursProblem`), полнота
  (`weekHoursComplete`, `fieldAnswered`), ячейки выгрузки по дням
  (`weekHoursCells`) — не трогаются, кроме дополнения новым видом дня (ниже).
- `cleaningSchedule` и его редактор периодичности; еженедельная уборка
  использует тот же новый редактор правил, что и часы, через
  `CLEANING_DAY_OPTIONS`.
- Экран проверки, экран правок и редактор команды получают новый редактор
  автоматически — через общий `FieldInput`.

## Дополнение модели: «по расписанию рейсов»

```ts
type DayHours =
  | { kind: 'allDay' }
  | { kind: 'none' }
  | { kind: 'windows'; windows: Window[] }
  | { kind: 'flightSchedule' }          // НОВОЕ: работает с первого до последнего вылета

type HoursOptions = {
  allDay: boolean
  flightSchedule: boolean               // НОВОЕ: разрешён ли этот вид у поля
  noneLabel: Localized
}
```

`flightSchedule: true` только у III.1.1 «Lounge Operating Hours». У пиковых
часов и уборки — `false`; значение с таким видом у них — отказ сервера, как
`allDay` там, где он не разрешён. День вида `flightSchedule` считается
отвеченным и несёт часы (для правила «хотя бы один день с часами»).

Хранится по дням, как всё остальное: «по расписанию рейсов» для всей недели —
семь дней `{ kind: 'flightSchedule' }`. Так модель остаётся однородной, а
выгрузка по дням честной. Редактор показывает это одним переключателем на
всё поле, а не по дням: смешивать «по рейсам» с часами в одной неделе
бессмысленно, и интерфейс такого не предлагает. (Значение, где так смешано,
пришедшее мимо интерфейса, сервер принимает — оно корректно по форме — и
редактор показывает правилами, как любое другое.)

## Модель редактора: правила

Правила — **представление**, не хранение. Две чистые функции в
`schedule.ts` переводят туда и обратно:

```ts
/** Диапазон, как его вводит оператор: конец меньше начала = следующий день. */
type Range = { from: Clock; to: Clock | null }

type RuleHours =
  | { kind: 'allDay' }
  | { kind: 'windows'; ranges: Range[] }   // 1..n; обычно один

type HoursRule = { days: Weekday[]; hours: RuleHours }

type HoursView =
  | { kind: 'flightSchedule' }
  | { kind: 'rules'; rules: HoursRule[] }

expandRules(view: HoursView): WeekHours      // правила → семь дней для хранения
collapseWeek(week: WeekHours): HoursView     // хранение → правила для показа
```

### `expandRules` — как правила ложатся в дни

- Каждый день из `rule.days` получает `hours` правила. День, которого нет ни
  в одном правиле, получает `{ kind: 'none' }` (закрыт). Дни в правилах не
  повторяются (редактор это гарантирует, см. ниже); если повторяются в
  значении, пришедшем мимо редактора, — побеждает последнее правило.
- Диапазон с `to > from` — обычный интервал этого дня.
- Диапазон с `to < from` — **ночной**: этот день получает `from–24:00`, а
  **следующий день** (по кругу: после Вс — Пн) получает `00:00–to`. Именно
  следующий, не этот же: «пн 02:00–01:00» означает открытие в понедельник и
  закрытие во вторник в час ночи; у лаунжа, закрытого по пятницам, четверговый
  ночной график даёт пятнице `00:00–01:00`, и это правда.
- Диапазон с `to === from` — отказ формы (пустой или суточный интервал через
  полночь не имеет смысла; для «круглые сутки» есть `allDay`).
- Незакрытый диапазон (`to === null`) даёт день с незакрытым интервалом —
  сохраняется, анкета неполна (как сегодня).
- Интервалы дня после раскладки упорядочиваются; наложение «хвоста» с
  предыдущего дня на собственные интервалы дня — отказ формы, который показывает
  редактор (тот же `INVALID_SCHEDULE`), например «пн 22:00–03:00» и «вт
  02:00–10:00».
- `view.kind === 'flightSchedule'` — семь дней `{ kind: 'flightSchedule' }`.

### `collapseWeek` — как дни собираются обратно в правила

1. Если все отвеченные дни — `flightSchedule`, это `{ kind: 'flightSchedule' }`.
2. Иначе для каждого дня D: если у D есть интервал `00:00–X`, а у предыдущего
   дня (по кругу) есть интервал, заканчивающийся `24:00`, — этот `00:00–X`
   считается хвостом предыдущего дня, и у предыдущего дня интервал `Y–24:00`
   становится ночным диапазоном `Y–X`. Исключение: день целиком `00:00–24:00`
   не «хвост», а полный день (такой день редактор и так хранит как `allDay`).
3. Дни с одинаковым набором диапазонов (после шага 2) объединяются в одно
   правило; порядок правил — по первому дню. Дни `none` и неотвеченные дни в
   правила не входят.
4. Неотвеченный день и закрытый день различаются только в подписи под
   правилами (см. ниже).

Свойство, закреплённое тестами: `expandRules(collapseWeek(w)) ≡ w` для любой
корректной недели, и `collapseWeek(expandRules(v)) ≡ v` с точностью до порядка
правил и дней. Шесть живых графиков из таблицы выше — литеральные фикстуры
этих тестов.

### Взаимоисключение дней

День принадлежит не более чем одному правилу. Нажатие дня в одном правиле
снимает его с любого другого — чистая функция `toggleDay(rules, ruleIndex,
day)` в `schedule.ts`. Иначе про один день существовали бы два ответа.

## Редактор

Компонент `HoursRulesEditor` заменяет `WeekHoursEditor` (тот удаляется вместе
со своими быстрыми действиями `applyToAll` / `applyToWeekdays` /
`applyToWeekend` / `copyPreviousDay` — в модели правил они не нужны: «одинаково
всю неделю» — это одно правило на семь дней, которое и так стоит по умолчанию).

```
Часы работы лаунжа

  [ ] По расписанию рейсов                        ← только у III.1.1

  Пн Вт Ср Чт Пт Сб Вс       с 09:00  до 21:00   [24ч]           ✕
  Пн Вт Ср Чт Пт Сб Вс       с 10:00  до 20:00   [24ч]           ✕
  + ещё режим

  Пятница — закрыто
```

- **Первое правило создаётся сразу со всеми семью днями.** Варианты 3, 4 и 6
  из таблицы — один шаг: ввести время, или нажать «24ч», или поставить «по
  расписанию рейсов».
- **Полоска дней** — семь компактных квадратов с двумя буквами, нажатые
  подсвечены тем же стилем `aria-pressed`, что чипы формы. Это один элемент на
  правило по восприятию. Тап по дню, занятому другим правилом, переносит его
  сюда.
- **Время** — пара `<input type="time">` без подписей «с/до» в виде отдельных
  слов на десктопе (подписи — `aria-label`); на мобильном подписи короткие.
  `[24ч]` — маленький чип-переключатель у пары времени: нажат — поля времени
  скрыты, правило `allDay` (только где `hoursOptions.allDay`).
- **Ночной диапазон**: когда `to < from`, под парой времени появляется одна
  тихая строка «до 01:00 следующего дня». Ничего вводить дополнительно не надо.
- **Второй интервал в правиле** (разрывной день, редкий) — маленькая иконка
  «+» справа от пары времени; появляется только когда пара заполнена. Второй
  диапазон встаёт строкой под первым с «×» у себя. Правило редактора: новый
  диапазон начинается там, где закончился предыдущий (существующий
  `nextWindowStart`).
- **«×»** у правила — только когда правил больше одного. Удаление правила
  делает его дни закрытыми (они появляются в строке под правилами).
- **«+ ещё режим»** — тихая ссылка под правилами. Новое правило создаётся
  **без дней**: оператор выбирает дни сам, они снимаются с прежнего правила.
  Пока у правила нет дней или времени, под полем стоит одна строка «Режим 2:
  выберите дни» / «…укажите время» — одна на поле, не на строку.
- **Строка закрытых дней**: «Пятница — закрыто», «Пн, Вт, Ср, Чт, Пт —
  закрыто». Слово берётся из `hoursOptions.noneLabel`: у пиковых часов —
  «нет пика», у уборки — «без уборки». Это часть ответа, поэтому она видна
  всегда, когда есть такие дни.
  Если правил нет вообще (оператор удалил всё или поле пустое) — «Дни не
  выбраны», и поле не считается отвеченным.
- **Никаких постоянных подсказок.** Отказ сервера — под редактором, как у всех
  полей. Иконка «+» без доступного действия просто не показывается (вместо
  выключенной кнопки с объяснением).
- **Старый текстовый ответ** — над редактором с пометкой, как сегодня
  (`form.freeFormAnswer`); первое правило под ним обычное, со всеми семью
  днями; текст остаётся видимым, пока не сохранено первое структурное
  значение.

Мобильный экран (375): правило занимает две строки — полоска дней; пара
времени с чипом «24ч». Горизонтальной прокрутки нет.

Уборка «еженедельно» использует тот же `HoursRulesEditor` с
`CLEANING_DAY_OPTIONS` (без «24ч», без «по рейсам», пустое — «без уборки»).

## Канонический текст

`formatWeekHours` печатает **правила**, а не дни: то, что оператор ввёл, в
том виде, в каком он думает.

- `Mon–Fri 09:00–21:00; Sat–Sun 10:00–20:00`
- `Mon–Fri 02:00–01:00 (next day); Sat–Sun 05:00–01:00 (next day)` /
  `Пн–Пт 02:00–01:00 (след. дня); Сб–Вс 05:00–01:00 (след. дня)`
- `Mon–Sun 24h` (`Пн–Вс Круглосуточно`)
- `Mon–Thu, Sat–Sun 09:00–21:00; Fri Closed`
- `Mon–Sun Flight schedule` (`Пн–Вс По расписанию рейсов`)
- Неотвеченные дни — `—`, как сегодня.

Группировка дней внутри правила — отрезками по порядку недели («Mon–Thu,
Sat–Sun»), несмежные дни через запятую.

Ячейки выгрузки **по дням** печатают хранимую, разбитую по суткам форму:
для №2 вторник — `00:00–01:00, 02:00–24:00`. Это сознательно: колонка дня
должна говорить, когда лаунж открыт именно в этот день. Ячейка дня вида
`flightSchedule` — `Flight schedule`.

Выгрузка отдельной анкеты печатает канонический текст (правилами), как и
экран проверки.

## Тексты

Новые ключи словаря (EN/RU): `schedule.flightSchedule` («Flight schedule» /
«По расписанию рейсов»), `schedule.nextDay` («next day» / «след. дня»),
`schedule.addRule` («+ another schedule» / «+ ещё режим»), `schedule.closedDays`
(«{days} — closed» / «{days} — закрыто»), `schedule.noDays` («No days selected»
/ «Дни не выбраны»), `schedule.rulePickDays` («Schedule {n}: pick the days» /
«Режим {n}: выберите дни»), `schedule.ruleSetTime` («Schedule {n}: set the
time» / «Режим {n}: укажите время»), `schedule.allDayShort` («24h» / «24ч»).
Удаляются: `schedule.sameAllWeek`, `schedule.copyPrevious`,
`schedule.copyToWorkdays`, `schedule.copyToWeekend`, `schedule.finishPrevious`,
`schedule.dayIsFull`, `schedule.dayUnanswered`, `schedule.windowUnfinished` (и
всё, что читало их).

## Проверки

- Юнит, `schedule.ts`: `expandRules`/`collapseWeek` на шести живых графиках
  (литеральные фикстуры) и на разрывном дне; свойства обратимости; ночной
  диапазон у воскресенья попадает в понедельник; `to === from` — отказ;
  наложение хвоста на свой интервал — отказ; `toggleDay` снимает день с другого
  правила; `flightSchedule` под запретом у пиковых — отказ.
- Юнит, форматирование: шесть строк канонического текста из таблицы, оба языка;
  ячейки дня для №2 — разбитая форма.
- `fields.test.ts`: `flightSchedule: true` только у III.1.1.
- Компонент (статичная разметка): первое правило со всеми днями; полоска дней;
  чип «24ч» только где разрешён; «×» отсутствует при одном правиле; строка
  закрытых дней; переключатель «по рейсам» только у III.1.1; старый текст с
  пометкой.
- e2e (`fill.spec.ts`): пересобрать сценарий расписания под новый редактор —
  вариант №1 (два режима, будни/выходные), затем вариант №2 (ночной, проверка
  подписи «следующего дня» и разбитой формы после перезагрузки через экран
  проверки), затем «по расписанию рейсов»; пиковые — без «24ч» и без «по
  рейсам».
- Break-verify каждого теста по правилу проекта.

## Вне объёма

Разбор старых текстовых ответов в правила; «первый/последний вылет» с
привязкой к фактическому расписанию рейсов (это просто состояние, без данных о
рейсах); сезонные исключения (III.1.2 без изменений).
