# Расписания: редактор правилами вместо сетки по дням

Дата: 2026-09-11. Статус: дизайн утверждён пользователем в разговоре по
интерактивному макету (десять шагов), включая два последних изменения —
кликабельный итог и переименование кнопки добавления.

Развивает спецификацию `2026-09-04-structured-schedules-design.md`. Хранение,
серверная проверка и выгрузка из неё остаются; меняются редактор, канонический
текст и одно дополнение модели интервала.

## Зачем

Первая версия редактора показывала семь раскрытых дней, у каждого — тринадцать
элементов (три кнопки состояния, копирование, две подписи, два поля времени,
«до конца дня», «×», метка, «+ интервал» и подсказка под ним). Семь дней × два
поля = больше ста элементов на одном шаге; всё сливалось. Пользователь: «ужасное
интерфейсное решение, всё сливается, куча кнопок».

Живые графики лаунжей, которые пользователь привёл как частые:

| № | Как говорят операторы |
|---|---|
| 1 | Пн–Пт 09:00–21:00; Сб–Вс 10:00–20:00 |
| 2 | Пн–Пт 02:00–01:00; Сб–Вс 05:00–01:00 (до часу ночи следующего дня) |
| 3 | Пн–Вс 07:00–22:00 |
| 4 | Пн–Вс 00:00–23:59 (круглосуточно) |
| 5 | Пн, Вт, Ср, Чт, Сб, Вс 09:00–21:00; пятница не работает |
| 6 | Пн–Вс «с первого вылета по последний вылет» (очень часто у небольших аэропортов); бывает и смешанно: «с 01:00 по последний рейс», «с первого рейса до 23:00» |

Плюс два требования: должна оставаться возможность задать в каждый день своё
время, и лаунж может работать всего пару дней в неделю.

Операторы думают **правилами** — «эти дни — такой режим», а не семью
отдельными днями. Пять из шести примеров — одно или два правила. Два примера
первая версия не выражала вовсе: переход через полночь (№2) и границы «первый
/ последний рейс» (№6).

## Решения пользователя

- Ввод — правилами: набор дней + режим. Семь разных дней — семь правил.
- Ночной график вводится как есть («02:00–01:00»), а **хранится разбитым по
  суткам**: «02:00–24:00» в этот день и «00:00–01:00» в следующий. Модель
  хранения не получает интервалов через полночь.
- «Первый рейс» и «последний рейс» — **значения границы интервала** вместо
  времени, а не отдельный режим на всё поле: так одинаково записываются
  «с первого до последнего», «с 01:00 до последнего», «с первого до 23:00».
- Дни, не попавшие ни в одно правило, — закрыты.
- Под редактором всегда виден **итог на неделю** — семь строк по дню; это и
  есть ответ лаунжа. Новое правило создаётся из итога: у строки дня есть
  «изменить», оно рождает правило уже с этим днём.
- Кнопка под правилами называется задачей оператора — «Другие часы для части
  дней», — а не механизмом («+ ещё режим»).

Уточнение, принятое при записи (пользователь сказал «грубо говоря 23:59»):
конец суток хранится как `24:00` — это уже законное значение `to` в модели,
оно не теряет минуту и сохраняет стык «24:00 → 00:00», по которому редактор
узнаёт ночной график при чтении. В выгрузке дня печатается `24:00`.

## Что НЕ меняется

- Хранение: `WeekHours` — семь дней, у дня `allDay` / `none` / `windows`,
  интервалы в пределах суток, без пересечений. Значение в том же jsonb-столбце,
  миграции нет. Уже сохранённые структурные ответы остаются валидными и
  читаются новым редактором без конверсии.
- Серверные ворота (`validateField` → `weekHoursProblem`), полнота
  (`weekHoursComplete`, `fieldAnswered`), ячейки выгрузки по дням
  (`weekHoursCells`) — дополняются границами-рейсами (ниже), остальное не
  трогается.
- `cleaningSchedule` и его редактор периодичности; еженедельная уборка
  использует тот же новый редактор правил через `CLEANING_DAY_OPTIONS`.
- Экран проверки, экран правок и редактор команды получают новый редактор
  автоматически — через общий `FieldInput`.

## Дополнение модели: границы «первый / последний рейс»

```ts
type Clock = string                                   // 'HH:MM', плюс '24:00' только как конец
type Window = {
  from: Clock | 'firstFlight'                         // НОВОЕ: маркер вместо времени
  to:   Clock | 'lastFlight' | null                   // НОВОЕ: маркер вместо времени; null — не дописан
}

type HoursOptions = {
  allDay: boolean
  flightBounds: boolean                               // НОВОЕ: разрешены ли маркеры у поля
  noneLabel: Localized
}
```

`flightBounds: true` только у III.1.1 «Lounge Operating Hours». У пиковых часов
и уборки — `false`; маркер у них — отказ сервера, как `allDay` там, где он не
разрешён.

Правила формы (`windowsProblem`), дополнение к существующим:

- Интервал с маркером на любой границе — **единственный** в своём дне: порядок
  и пересечение с другими интервалами того же дня для него не определены,
  второй интервал рядом — отказ (`'order'`).
- Интервал с маркером не бывает ночным: `firstFlight → 23:00` и
  `01:00 → lastFlight` лежат в своих сутках целиком; редактор не предлагает
  для него «следующего дня», а `expandRules` не разбивает.
- Полнота: интервал `firstFlight → lastFlight` дописан (оба конца заданы);
  `01:00 → null` — не дописан, как сегодня.

Маркеры хранятся по дням, как и всё остальное: семь дней с
`{ from: 'firstFlight', to: 'lastFlight' }` — это «по расписанию рейсов» для
всей недели. Ячейка выгрузки дня печатает маркер словами (ниже).

## Модель редактора: правила

Правила — **представление**, не хранение. Две чистые функции в
`schedule.ts` переводят туда и обратно:

```ts
/** Диапазон, как его вводит оператор: у времён конец меньше начала = следующий день. */
type Range = { from: Clock | 'firstFlight'; to: Clock | 'lastFlight' | null }

type RuleHours =
  | { kind: 'allDay' }
  | { kind: 'windows'; ranges: Range[] }   // 1..n; обычно один

type HoursRule = { days: Weekday[]; hours: RuleHours }

expandRules(rules: HoursRule[]): WeekHours      // правила → семь дней для хранения
collapseWeek(week: WeekHours): HoursRule[]      // хранение → правила для показа
```

### `expandRules` — как правила ложатся в дни

- Каждый день из `rule.days` получает `hours` правила. День, которого нет ни
  в одном правиле, получает `{ kind: 'none' }` (закрыт). Дни в правилах не
  повторяются (редактор это гарантирует, см. ниже); если повторяются в
  значении, пришедшем мимо редактора, — побеждает последнее правило.
- Диапазон из двух времён с `to > from` — обычный интервал этого дня.
- Диапазон из двух времён с `to < from` — **ночной**: этот день получает
  `from–24:00`, а **следующий день** (по кругу: после Вс — Пн) получает
  `00:00–to`. Именно следующий, не этот же: «пн 02:00–01:00» означает открытие
  в понедельник и закрытие во вторник в час ночи; у лаунжа, закрытого по
  пятницам, четверговый ночной график даёт пятнице `00:00–01:00`, и это
  правда.
- Диапазон из двух времён с `to === from` — отказ формы (для «круглые сутки»
  есть `allDay`).
- Диапазон с маркером — интервал этого дня как есть, без разбиения.
- Незакрытый диапазон (`to === null`) даёт день с незакрытым интервалом —
  сохраняется, анкета неполна (как сегодня).
- Интервалы дня после раскладки упорядочиваются; наложение «хвоста» с
  предыдущего дня на собственные интервалы дня — отказ формы, который
  показывает редактор (тот же `INVALID_SCHEDULE`), например «пн 22:00–03:00» и
  «вт 02:00–10:00».

### `collapseWeek` — как дни собираются обратно в правила

1. Для каждого дня D: если у D есть интервал `00:00–X` (X — время), а у
   предыдущего дня (по кругу) есть интервал `Y–24:00` (Y — время), — этот
   `00:00–X` считается хвостом предыдущего дня, и у предыдущего дня интервал
   становится ночным диапазоном `Y–X`. Исключение: день целиком `00:00–24:00`
   не «хвост», а полный день (редактор и так хранит такой день как `allDay`).
   Интервалы с маркерами в склейке не участвуют.
2. Дни с одинаковым набором диапазонов (после шага 1) объединяются в одно
   правило; порядок правил — по первому дню. Дни `none` и неотвеченные дни в
   правила не входят.
3. Неотвеченный день и закрытый день различаются только в итоге (см. ниже).

Свойство, закреплённое тестами: `expandRules(collapseWeek(w)) ≡ w` для любой
корректной недели, и `collapseWeek(expandRules(r)) ≡ r` с точностью до порядка
правил и дней. Шесть живых графиков из таблицы выше (включая смешанные границы
из №6) — литеральные фикстуры этих тестов.

### Взаимоисключение дней

День принадлежит не более чем одному правилу. Нажатие дня в одном правиле
снимает его с любого другого — чистая функция `toggleDay(rules, ruleIndex,
day)`. Вынос дня из итога в новое правило — чистая функция
`splitDay(rules, day)`: снимает день со его правила и создаёт новое правило
`{ days: [day], hours: { kind: 'windows', ranges: [{ from: '', to: null }] } }`
в конце списка. Обе в `schedule.ts`.

## Редактор

Компонент `HoursRulesEditor` заменяет `WeekHoursEditor` (тот удаляется вместе
с быстрыми действиями `applyToAll` / `applyToWeekdays` / `applyToWeekend` /
`copyPreviousDay`, `dayCopyable`, маркерами «не отвечено / не закончено» и
объяснениями недоступности «+ интервал» — в модели правил всё это не нужно).

```
Часы работы лаунжа

  Режим 1
  [Пн][Вт][Ср][Чт][Пт] Сб  Вс        с 09:00 или первый рейс   до 21:00 или последний рейс   [24ч]
                                                                                              (×)
  Режим 2
   Пн  Вт  Ср  Чт  Пт [Сб][Вс]       с первого рейса ×          до 23:00 или последний рейс   [24ч]   ×

  Другие часы для части дней

  ────────────────────────────────
  Итог на неделю
  Пн   09:00–21:00                 изменить
  Вт   09:00–21:00                 изменить
  …
  Сб   с первого рейса до 23:00    изменить
  Вс   с первого рейса до 23:00    изменить
```

- **Первое правило создаётся сразу со всеми семью днями.** Варианты 3, 4 и 6
  — один шаг: ввести время, или нажать «24ч», или заменить обе границы на
  рейсы.
- **Подпись «Режим N»** над каждым правилом — тихая, 12px; она даёт строкам
  имя, на которое ссылается подсказка о незаполненности.
- **Полоска дней** — семь компактных квадратов с двумя буквами, нажатые
  подсвечены тем же стилем `aria-pressed`, что чипы формы. Тап по дню,
  занятому другим правилом, переносит его сюда.
- **Границы** — пара `<input type="time">`; подписи «с» / «до» коротким
  словом; у поля III.1.1 после каждого поля времени стоит тихая текстовая
  ссылка «или первый рейс» / «или последний рейс». Нажатая ссылка заменяет
  поле словами «с первого рейса» / «до последнего рейса» с маленьким «×»,
  возвращающим поле времени. У пиковых и уборки ссылок нет.
- **`[24ч]`** — чип у пары времени (только где `hoursOptions.allDay`);
  нажат — поля времени скрыты, правило `allDay`.
- **Ночной диапазон**: когда оба конца — времена и `to < from`, под правилом
  одна тихая строка «до 01:00 следующего дня».
- **Второй интервал в правиле** (разрывной день, редкий) — маленькая иконка
  «+» справа от пары времени; видна только когда пара заполнена временами
  (у интервала с маркером второго не бывает). Новый диапазон начинается там,
  где закончился предыдущий (существующий `nextWindowStart`).
- **«×»** у правила — только когда правил больше одного. Удаление правила
  делает его дни закрытыми.
- **«Другие часы для части дней»** — тихая ссылка под правилами; создаёт
  правило без дней (для тех, кто идёт сверху вниз). Главный путь — из итога.
- **Итог на неделю** — семь строк «день — текст дня» (`formatDayHours`, тот же
  текст, что на экране проверки и в ячейке выгрузки), закрытые дни серым.
  У каждой строки ссылка **«изменить»**: она вызывает `splitDay` — день
  уходит в новое правило с пустым временем, курсор в его поле «с». Так
  оператор исправляет тот день, который в итоге не сошёлся, не зная слова
  «режим». Неотвеченный день печатается «—».
- **Одна строка о незаполненности** под полем, не на правило: «Режим 2:
  выберите дни» / «Режим 2: укажите время» — только пока это так.
- **Никаких постоянных подсказок.** Отказ сервера — под редактором, как у всех
  полей.
- **Старый текстовый ответ** — над редактором с пометкой, как сегодня
  (`form.freeFormAnswer`); первое правило под ним обычное, со всеми семью
  днями; текст остаётся видимым, пока не сохранено первое структурное
  значение.

Мобильный экран (375): правило занимает две-три строки — полоска дней; «с …»;
«до …» с чипом «24ч». Итог — те же семь строк. Горизонтальной прокрутки нет.

Уборка «еженедельно» использует `HoursRulesEditor` с `CLEANING_DAY_OPTIONS`
(без «24ч», без ссылок-рейсов, пустое — «без уборки»).

## Канонический текст

`formatDayHours` учится печатать маркеры; `formatWeekHours` печатает
**правила** (через `collapseWeek`), а не дни, — в том виде, в каком оператор
думает.

- `Mon–Fri 09:00–21:00; Sat–Sun 10:00–20:00`
- `Mon–Fri 02:00–01:00 (next day); Sat–Sun 05:00–01:00 (next day)` /
  `Пн–Пт 02:00–01:00 (след. дня); Сб–Вс 05:00–01:00 (след. дня)`
- `Mon–Sun 24h` (`Пн–Вс Круглосуточно`)
- `Mon–Thu, Sat–Sun 09:00–21:00; Fri Closed`
- `Mon–Sun first flight–last flight` (`Пн–Вс с первого рейса до последнего`)
- `Sat–Sun first flight–23:00` (`Сб–Вс с первого рейса до 23:00`),
  `01:00–last flight` (`с 01:00 до последнего рейса`)
- Неотвеченные дни — `—`.

Группировка дней внутри правила — отрезками по порядку недели («Mon–Thu,
Sat–Sun»), несмежные через запятую. Слово закрытого дня — из `noneLabel`.

Ячейки выгрузки **по дням** печатают хранимую форму: для №2 вторник —
`00:00–01:00, 02:00–24:00`; для №6 — `first flight–last flight`. Колонка дня
говорит, когда лаунж открыт именно в этот день.

Выгрузка отдельной анкеты печатает канонический текст (правилами), как и
экран проверки.

## Вне объёма

Разбор старых текстовых ответов в правила; привязка «первого/последнего
рейса» к фактическому расписанию рейсов (это маркер, без данных о рейсах);
сезонные исключения (III.1.2 без изменений).
