# Типы поля «телефон» и «почта»: маски, плейсхолдеры, проверка на сервере

Дата: 2026-09-04. Статус: дизайн утверждён пользователем в разговоре.

## Зачем

Контактные поля анкеты — обычный текст без правил: оператор может набрать в
телефон буквы, в почту — что угодно, и анкета это примет. Нужны подсказка
формата (плейсхолдер), запрет недопустимых символов при наборе и проверка на
сервере, чтобы значение, обошедшее браузер, тоже не прошло.

## Объём

**Чистые поля — получают тип и правила.**

| Ключ | Поле | Новый тип |
|---|---|---|
| II.1.2 | Contact Number - Lounge Operations Manager | `phone` |
| II.2.1 | Shift Mobile / Duty Phone Number | `phone` |
| II.3.2 | Finance SPOC - Contact No | `phone` |
| II.4.1 | Telephone - Landline/Fixline No - Lounge (If Any) | `phone` |
| II.4.2 | Fax Number (If Any) | `phone` |
| II.1.3 | Email Address - Lounge Operations Manager | `email` |
| II.3.3 | Finance SPOC - Email address | `email` |

**Смешанные поля — остаются `text`, без изменений**: II.2.2 «Alternative
Operation Contact (name/email/phone)», II.2.3 «Preferred Communication
Channel». В одном поле несколько разных вещей, одно правило к ним не
подходит; решение пользователя — оставить свободным текстом.

Вне объёма: разбиение смешанных полей, справочник форматов по странам,
нормализация уже сохранённых значений, изменения экспорта и реестра.

## Подход

Два новых значения в `FieldType` (`src/form-schema/fields.ts`): `'phone'` и
`'email'`. Всё остальное **выводится из типа**, в духе правила проекта «одно
правило в одном месте»:

- ввод в форме и в редакторе команды (`FieldInput` — общий компонент обоих
  экранов);
- проверка на сервере (`validateField` в `src/form-schema/validation.ts`,
  вызывается из `saveFieldValue`);
- сид (`scripts/seed-dev.ts` перестаёт угадывать почту по подписи поля
  регэкспом `EMAIL_LABEL` и смотрит на тип);
- выгрузка и отрисовка значений — как у `text`, значение остаётся строкой.

Отвергнутые варианты: пометка `format` при типе `text` (два признака про одно
поле, могут разойтись); маска только в браузере (сервер — ворота, браузер —
подсказка; правило проекта).

## Правила

### Телефон (`phone`)

- Допустимые символы при наборе: `+` только первым символом, цифры, пробел,
  `(`, `)`, `-`. Всё остальное при наборе не появляется; при вставке из
  буфера недопустимое вырезается, `+` не в начале — тоже.
- Серверное правило: после удаления пробелов, скобок и дефисов остаётся
  `^\+?\d{6,15}$` (верхняя граница — E.164). Иначе отказ с текстом
  «Enter the number in international format, e.g. +90 212 000 00 00» /
  «Введите номер в международном формате, например +90 212 000 00 00».
- Пустое значение: у обязательного поля — прежний отказ «Поле обязательно»,
  у необязательного (II.4.1, II.4.2) — допустимо.
- Плейсхолдер: `+90 212 000 00 00`. `inputMode="tel"`, `type="tel"`,
  `autoComplete="tel"`.

### Почта (`email`)

- Допустимые символы при наборе: любые, кроме пробельных. Пробел не
  появляется; при вставке пробелы вырезаются. Регистр не меняется.
- Серверное правило: `^[^\s@]+@[^\s@]+\.[^\s@]+$` — одна `@`, без пробелов,
  домен с точкой. Иначе отказ «Enter a valid email address, e.g.
  name@company.com» / «Введите адрес почты, например name@company.com».
- Пустое значение — как у телефона.
- Плейсхолдер: `name@company.com`. `inputMode="email"`, `type="email"`,
  `autoComplete="email"`.

Тексты отказов — `Localized`, объявлены рядом с `REQUIRED` в `validation.ts`
и **не дублируются** в компонентах: браузер показывает то, что вернул
сервер (`autosave.rejected[field.key]` → `FieldInput error`).

## Поведение на экранах

- **Форма заполнения.** Автосохранение с задержкой 600 мс как сейчас; отказ
  сервера появляется под полем тем же механизмом, что у других отказов, и
  снимается следующей допустимой записью. Полоса «Saved» на отказ не
  загорается (существующее правило).
- **Экран проверки, редактор команды.** Тот же `FieldInput`, те же фильтры
  символов и тот же отказ внутри редактора (`EditOutcome`), черновик не
  теряется.
- **Экран правок оператора.** Тот же `FieldInput`.
- **Старые ответы.** Хранятся как есть и показываются как есть. Любая правка
  проходит новые правила — сохранить можно только допустимое значение.
- **Плейсхолдер** — атрибут `placeholder` инпута; поле `example`
  (`field-example` под инпутом) у этих семи полей не используется, чтобы не
  говорить одно и то же дважды.

## Данные и совместимость

- Схема БД не меняется: `field_values.value` остаётся текстом. Миграции нет.
- Экспорт: колонки те же, значения те же.
- `assertNeverFieldType`-переключатели (`validateField`, `FieldInput`,
  `renderValues`, сид) получают ветки для двух новых типов — компилятор
  укажет каждое место.

## Проверки

- **Юнит, `validation.test.ts`:** таблицы верных и неверных значений для
  обоих типов; пустое у обязательного и у необязательного; текст отказа
  на обоих языках; `text`-поля не задеты.
- **Юнит, компонент `FieldInput`:** буква в телефоне не появляется, `+` в
  середине вырезается, вставка `+90 (212) 000-00-00` сохраняется как есть;
  пробел в почте не появляется; плейсхолдеры и `inputMode` на месте.
- **Юнит, `fields.test.ts`:** семь ключей закреплены за типами буквально,
  II.2.2 и II.2.3 — `text`.
- **Сид:** для `phone` пишет допустимый номер, для `email` — `seedEmailFor`.
- **e2e, `fill.spec.ts`:** оператор набирает мусор в телефон — поле пустое;
  вводит почту без `@` — под полем отказ; исправляет — «Saved», отказ снят.
- Break-verify каждого теста по правилу проекта.
