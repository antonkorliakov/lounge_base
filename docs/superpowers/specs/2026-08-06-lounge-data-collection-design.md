# Онлайн-система сбора данных по лаунжам

**Дата:** 2026-08-06
**Статус:** дизайн согласован

## 1. Задача

Заменить сбор данных по бизнес-лаунжам через рассылку Excel-файла на веб-систему, доступную с телефона, со встроенным процессом проверки данных.

Источник требований — существующая форма `Global Onboarding Form 1.xlsx`. Сегодня она рассылается операторам лаунжей, заполняется в Excel, возвращается по почте и проверяется вручную. Замечания живут в переписке, версии файлов расходятся, состояние проверки нигде не зафиксировано.

**Цели:**

1. Заполнение анкеты с телефона, в том числе прямо в лаунже
2. Проверка данных как процесс с фиксированными состояниями, а не переписка
3. Возврат на правку без повторного заполнения всей анкеты
4. Выгрузка в том же формате, в каком форма существует сегодня

## 2. Объём анкеты

Замеры по исходному файлу (листы `General Lounge Information` и `Services & Amenities`; листы `Approuved by DF` в систему не переносятся).

| Что | Количество |
|---|---|
| Плоские поля (разделы I–V) | 67 |
| Заголовки подразделов (не поля) | 12 |
| Позиции услуг и питания | 58 (44 услуги + 14 F&B) |
| Атрибутов у каждой позиции | 6 |
| Значений в матрице услуг | 348 |
| Свободные поля «прочее» | 2 |
| **Всего точек данных** | **417** |
| Фотографии | 4–5 |

Разделы плоской части: `I. Профиль и коммерческие детали` (15), `II. Контакты` (11 в 4 подразделах), `III. Информация о лаунже` (36 в 8 подразделах), `IV. Размещение логотипа` (4), `V. Срок действия соглашения` (1).

## 3. Архитектура

Next.js (App Router) на Vercel, Postgres, Vercel Blob для фотографий. Один деплой из репозитория `lounge_base`.

| Модуль | Ответственность | Зависит от |
|---|---|---|
| `form-schema` | Декларативное описание анкеты: разделы, поля, типы, списки значений, обязательность, условные правила, подсказки, примеры | — |
| `db` | Схема БД и запросы | — |
| `submissions` | Черновик, автосохранение, полнота, переходы статусов | `form-schema`, `db` |
| `review` | Подтверждение блоков, замечания к полям | `db` |
| `export` | Сборка xlsx и CSV | `form-schema`, `db` |
| `access` | Токены-приглашения, magic-link для команды | `db` |
| `i18n` | Словари EN/RU | — |
| `web` | Публичная форма и внутренний кабинет | все выше |

**`form-schema` — центральное решение.** Это чистые данные и типы: ни React, ни обращений к БД. Из него выводятся три вещи, которые иначе разъезжаются между собой: рендер формы, валидация (клиентская и серверная) и колонки выгрузки. Любое изменение анкеты делается в одном месте.

**Два интерфейса, одно ядро:**

- `/f/<token>` — публичная форма, мобильная, без регистрации
- `/admin` — внутренний кабинет: список лаунжей с фильтрами, просмотр анкеты, проверка, выгрузка

Требования у них разные: публичная часть работает на телефоне с нестабильной связью, внутренняя — рабочий инструмент за десктопом.

## 4. Модель данных

```
lounges         id, country, city, airport, iata_code, name, provider
submissions     id, lounge_id, status, filler_token_id, reviewer_id,
                created_at, submitted_at, decided_at
field_values    submission_id, field_key, value (JSONB)
service_values  submission_id, item_key, available, charge_type, price,
                currency, slot_minutes, booking_required, details
photos          submission_id, slot, blob_key, caption, uploaded_at
block_reviews   submission_id, block_key, confirmed_by, confirmed_at
field_flags     submission_id, field_key, reason, comment, created_by,
                created_at, resolved_at
events          submission_id, actor, action, payload, at
```

**Плоские поля через `field_key` + JSONB, а не 67 колонок.** Анкета живая — в исходном файле видны рабочие пометки, состав полей будет меняться. Отдельные колонки означают миграцию БД на каждую правку формулировки. Типы при этом не теряются: они заданы в `form-schema`, валидация строится из неё.

**Услуги — отдельная таблица с колонками.** Структура однородна и стабильна: 6 атрибутов у каждой из 58 позиций. Колонки дают осмысленную валидацию (цена обязательна при `Chargeable`) и нормальные запросы вроде «лаунжи с душем».

**`field_flags` и `block_reviews` разделены,** потому что подтверждение идёт по блокам, а замечания — по полям. См. раздел 6.

## 5. Схема анкеты

### Типы полей

| Тип | Где встречается |
|---|---|
| `text` / `textarea` | названия, адреса, описания расположения |
| `date` | `I.1 Lounge Open Date`, `V. Term End date` |
| `number` | вместимость, часы, время трансфера, налог (%) |
| `select` | 16 списков значений |
| `select_with_detail` | варианты `Other (Specify→)` и `Yes (Specify→)` требуют текст |
| `multi_select` | `III.6.6 Arrival / Departure / Transit` — «укажите все применимые» |
| `template` | фразы с пропусками, см. ниже |
| `photo_slot` | именованные слоты фотографий |

### Поля-шаблоны

В Excel часть полей сделана как текст с пропусками, потому что иначе было нельзя:

- `«Access is permitted ( ) hours prior to scheduled flight departure»`
- `«No Charge for Children under ( ) years old»`
- `«Child rate: children from ( ) to ( ) years old. Adult rate: children ( ) years and older»`

В веб-форме это отдельные числовые поля, а фраза собирается автоматически. Данные становятся машиночитаемыми, а в выгрузке фраза выглядит как в оригинале.

### Списки значений

Переносятся из `dataValidation` исходного файла — 16 уникальных списков: этажи, типы терминалов, `Before / After SHA`, `Airside / Landside`, `Before / After Immigration`, способы перехода между терминалами, политика при переполнении, доступ для колясок и животных, платность услуги (`Complimentary / Chargeable / Both`), политика вейпинга и т. д.

`«Allowed, Not allowed»` и `«Allowed, Not Allowed»` отличаются в исходнике только регистром. В схеме это один список; при импорте старых файлов оба написания приводятся к нему.

### Обязательность

Не «всё обязательно», как написано в шапке Excel: в самой форме есть `(If Any)`, `if applicable`, `leave blank if not applicable`. Обязательность задаётся по полю, плюс условные правила:

- цена обязательна, если услуга `Chargeable` или `Both`
- уточнение обязательно, если выбрано `Other (Specify→)` или `Yes (Specify→)`
- список авиакомпаний обязателен при `Specific airlines passengers allowed`

## 6. Бизнес-процесс

### Статусы

```
draft ──отправить──▶ submitted ──принять──▶ approved
                        │  ▲
          вернуть на    │  │  отправить
            правку      ▼  │   заново
                  changes_requested
```

Отдельного статуса «в работе у ревьюера» нет — у `submitted` есть `reviewer_id`. Тот же смысл без лишнего состояния.

- **`draft`** — заполняющий правит что угодно, автосохранение по каждому полю
- **`submitted`** — форма для заполняющего закрыта, иначе ревьюер проверяет плывущие данные
- **`changes_requested`** — открыты только отмеченные поля
- **`approved`** — данные заморожены, доступна выгрузка

### Проверка

Проверяет один человек; разделения по ролям нет.

Требовать явного «принято» на каждую из 417 точек данных нереально, но и приём одной кнопкой проверкой не является. Поэтому **подтверждение по блокам, замечания по полям**:

- **27 блоков**, повторяющих структуру исходной формы: `I. Профиль` (1), подразделы `II` и `III` (12), `IV. Логотип` (1), `V. Срок действия` (1), группы услуг и питания (11), `Фото` (1)
- ревьюер подтверждает блок целиком
- внутри блока помечает проблемные поля с комментарием
- анкета принимается, когда подтверждены все блоки и нет открытых замечаний

**На что вешается замечание.** `field_flags.field_key` адресует то, что заполняющий видит как один вопрос: для плоской части — поле (67 ключей), для матрицы услуг — позицию целиком (58 ключей), а не отдельный атрибут, плюс слоты фотографий. Претензия к конкретному атрибуту («не указана цена») выражается текстом комментария. Иначе на возврате пришлось бы открывать заполняющему одну ячейку в отрыве от остальных пяти, что бессмысленно: он всё равно правит позицию целиком.

**Ввод замечания** — три шага, без модальных окон:

1. При наведении на строку справа проявляется кнопка «отметить» (в покое скрыта, иначе кнопки рябят на каждой строке)
2. По клику под строкой раскрывается поле комментария с готовыми причинами одним кликом: «не заполнено», «нужна расшифровка», «противоречит другому полю», «неверный формат». Причина необязательна, комментарий пишется свободно
3. После сохранения строка помечена, блок нельзя подтвердить. Ревьюер может снять замечание сам

**«Вернуть на правку» доступно, не дожидаясь конца проверки.** Если проблема видна в третьем блоке из двадцати, размечать остальные семнадцать смысла нет.

### Возврат на правку

Заполняющий видит **только отмеченные поля** с комментариями — не всю анкету. Подтверждённые блоки остаются подтверждёнными: после повторной отправки ревьюер перепроверяет лишь исправленное. Это то, что делает второй и третий круг дешёвыми.

Уведомления о смене статуса — на email. Мессенджеры в первую версию не входят: ссылку всё равно отправляет человек.

## 7. Заполнение формы

Разделы I–V (67 полей) — обычные экраны, сгруппированные по подразделам исходной формы.

Матрица услуг (58 × 6) заполняется **в два прохода**:

**Проход 1 — что есть в лаунже.** Чек-лист всех 58 позиций, одно решение на позицию, сгруппировано по разделам исходной формы (`Comfort & Environment`, `Connectivity & Business`, …, `Meal Types`, `Beverages`). Заполняющий делает 58 однотипных дешёвых решений подряд, без переключения контекста.

**Проход 2 — детали по отмеченному.** Для каждой доступной услуги спрашиваются оставшиеся 5 атрибутов: платность, цена и валюта, длительность слота, нужна ли бронь, детали. В типичном лаунже это порядка 20 коротких экранов вместо 58.

Обоснование: большинство позиций в реальном лаунже — «нет». Два прохода отделяют «что у вас есть» от «расскажите подробнее», вместо 58 переключений между этими вопросами.

Возврат к проходу 1 доступен всегда — если заполняющий ошибся в отборе.

## 8. Доступ

**Заполняющий — по ссылке с токеном, без регистрации.** Оператор лаунжа в Стамбуле не станет заводить аккаунт ради одной анкеты. Токен привязан к конкретному лаунжу, имеет срок жизни и продлевается при возврате на правку.

**Внутренняя команда — magic-link на рабочую почту.** Паролей нет, управлять ими не нужно, команда небольшая.

## 9. Фотографии

Исходная форма просит 4–5 снимков и перечисляет, какие именно. Поэтому вместо безымянной загрузки — **именованные слоты**: вход, стойка регистрации, ориентиры рядом, плюс свободные дополнительные. Ревьюер тогда видит не «5 файлов», а «нет фото стойки», и может отметить именно это.

Снимки уменьшаются в браузере до загрузки: пять фотографий с телефона на аэропортовом Wi-Fi иначе не уйдут.

## 10. Выгрузка

xlsx, повторяющий структуру исходного файла: те же два листа, разделы и нумерация. Файл собирается из `form-schema`, поэтому при изменении анкеты выгрузка не расходится с формой. Дополнительно — CSV по всем лаунжам для аналитики.

## 11. Надёжность и валидация

**Главный риск — потеря введённого.** Заполнить сотни полей и потерять их из-за обрыва связи означает, что второй раз человек это делать не станет. Меры:

- сохранение на сервер по каждому изменённому полю
- локальная копия черновика в браузере как страховка: при пропаже связи введённое не исчезает и досылается при восстановлении

Полноценный офлайн-режим не закладывается — несоразмерно задаче.

**Валидация** живёт в `form-schema` и выполняется дважды: на клиенте для подсказок, на сервере как источник истины. Клиенту доверять нельзя, и это единственный способ гарантировать соответствие данных схеме.

## 12. Локализация

Переключатель EN/RU, обе части интерфейса локализованы. Формулировки полей анкеты берутся из исходного файла как английский вариант; русский перевод хранится рядом в том же `form-schema`.

## 13. Тестирование

- **`form-schema`** — целостность схемы: уникальность ключей, у каждого `select` есть значения, условные правила ссылаются на существующие поля, у каждого поля есть оба перевода
- **`submissions`** — переходы статусов: нельзя принять анкету с открытым замечанием, нельзя редактировать в `submitted`, подтверждённые блоки переживают возврат на правку
- **`export`** — обратный прогон: выгрузили, загрузили обратно, данные совпали
- **Сквозной сценарий** — заполнил → отправил → вернули с замечанием → исправил → приняли

## 14. Не входит в первую версию

- Полноценный офлайн-режим
- Уведомления в мессенджеры
- Разделение проверки по ролям (операционист / финансист)
- Публичный каталог лаунжей для конечных пользователей
- Импорт исторических Excel-файлов (схема к нему готова, но это отдельная задача)
